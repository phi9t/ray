* Scope

This document is the canonical engineering runbook for building and validating
Ray in the Zephyr ~sglang~ container while enforcing:

- Spack-owned core runtime/toolchain (including Python, torch/jax core)
- uv-only Python dependency management for layered installs
- Bazel-based compilation for ~//:ray_pkg~

It includes:

- The stable workflow (build, test, install, runtime validation)
- The real failure chain encountered and fixes applied
- Hard constraints and non-negotiable policies
- Failure modes, diagnostics, and recovery playbooks

* Invariants and Policy

** Mandatory Rules

1. Always activate Spack env before build/test/install.
2. Always use uv for Python installation operations.
3. Always bind uv env to Spack Python with system packages enabled.
4. Never override Spack core torch/jax stack from uv install.
5. For native-extension builds, Python C/C++ headers must come from Spack Python.

* Real Failure Timeline and Fixes

** Failure 1: ~//:ray_pkg~ packaging permission denied

Symptom:

- build reached genrule ~//:ray_pkg~
- failed at:
  - ~rm -rf python/ray/core/generated ...~
  - ~Permission denied~

Root cause:

- bind-mounted generated protobuf directories were root-owned from prior runs
- current run used non-root host UID/GID in container
- Bazel genrule could not clean generated output path

Fix:

- add preflight ownership normalization for:
  - ~python/ray/core/generated~
  - ~python/ray/serve/generated~

** Failure 2: uv cache initialization permission denied

Symptom:

- stage ~[3/4]~ failed with:
  - ~Failed to initialize cache at /mnt/shared/uv_cache/ray-install~
  - ~Permission denied (os error 13)~

Root cause:

- shared uv cache subtree ownership incompatible with current UID/GID

Fix:

- in preflight:
  - ~mkdir -p ${UV_CACHE_INNER}~
  - ~chown -R ${HOST_UID}:${HOST_GID} ${UV_CACHE_INNER}~

** Hardening Decision: Hard-fail preflight

Current state:

- ownership normalization commands are strict (no ~|| true~)
- if chown fails, script exits immediately
- this prevents hidden partial runs and non-deterministic failures later in pipeline

* Why the Current Workflow is Stable

1. ABI/toolchain consistency:
   - compile + install tied to Spack Python and Spack environment
2. Layering discipline:
   - uv excludes torch/jax/jaxlib/triton, preventing accidental replacement of Spack core
3. Deterministic filesystem ownership:
   - preflight avoids UID/GID drift from mixed root/non-root container writes
4. Real runtime validation:
   - final stage validates task scheduling, actor state, object store roundtrip

** uv layered install from local source

#+begin_src bash

PY_INCLUDES="$(${SPACK_PYTHON}-config --includes)"

uv venv --python "$SPACK_PYTHON" --system-site-packages .venv-ray-pkg-py313
source .venv-ray-pkg-py313/bin/activate

jax
jaxlib
triton

CPPFLAGS="${PY_INCLUDES} ${CPPFLAGS:-}" \
SKIP_BAZEL_BUILD=1 RAY_BUILD_REDIS=0 \
uv pip install --excludes /tmp/ray_uv_excludes.txt ./python
#+end_src

** Python ABI mismatch for ~_raylet.so~

Symptom:

- undefined symbol errors at import time (example historically: ~PyImport_AddModuleRef~)

Check:

#+begin_src bash
python -c "import sys; print(sys.version)"
python - <<'PY'
import pathlib, ray
print(pathlib.Path(ray.__file__).with_name('_raylet.so'))
PY
#+end_src

Mitigation:

- ensure venv Python and build Python are the same minor version
- enforce Spack Python minor version gate before install

** ~release-ready~ fails due to missing ~torch~ or ~jax~

Symptom:

- release log contains:
  - ~torch import failed in Ray runtime context~ or
  - ~jax import failed in Ray runtime context~ or
  - ~module is not from Spack paths~

Root cause:

- venv runtime context does not see Spack site-packages after activation
- or Spack environment activation is not applied correctly

Check:

#+begin_src bash
./dev/zephyr/zephyr_ray.sh debug-env
./dev/zephyr/zephyr_ray.sh release-ready
#+end_src

Recover:

- ensure Spack env activation is healthy (~spack env activate /opt/spack_env/default~)
- ensure release gate runtime has Spack site paths in ~PYTHONPATH~
- ensure required modules resolve under ~\/opt\/spack_store\/...~ and not non-Spack paths
- re-run release gate after fixing env path/mount issues

** Bazel cache write failures

Symptom:

- ~mkdir(... output root ...): Permission denied~

Mitigation:

- use writable ~BAZEL_OUTPUT_ROOT~ override, e.g.:

#+begin_src bash
BAZEL_OUTPUT_ROOT=/workspace/ray/.bazel-output-root ./dev/zephyr_ray_e2e_validate.sh
#+end_src

* Performance / Security / Regression Notes

** Performance

- Shared Bazel cache substantially reduces iterative build time.
- If Docker ~\/dev\/shm~ is too small, Ray may fallback object store to ~\/tmp~, hurting performance.

** Security and least privilege

- Runtime build/test/install containers run as host UID/GID, not root.
- Only preflight ownership correction runs with default container privileges and is scoped to known paths.

** Regression risk areas

- Upstream grpc/third-party changes can invalidate module dependency patches.
- Spack Python minor version bumps can break expected ABI or packaging assumptions.
- Shared cache path policy changes can reintroduce permission instability.
